# Companion 权限与安全中心 + React UI 重构设计

**Goal**

把 companion 旧托盘界面重构为一套正式的 React 面板，并新增一个清晰、可控、默认安全的“权限与安全”子页面，让用户能看见：

- 系统层是否已授权
- Companion 是否在使用这项能力
- 高风险能力当前是否开启
- 插件动作为什么成功、为什么被拦截、为什么需要确认

同时保证：

- 权限启用必须由用户手动确认
- 高风险能力默认关闭
- 管理员动作即使总开关开启，也要每次再确认一次
- 权限拦截不会把主服务状态误显示成故障

**Decision**

采用“整套 UI 统一迁移 + 独立权限子页面 + 双层状态模型”的方案。

- 整个 companion 托盘界面统一迁移到：
  - `Tauri 2`
  - `Vite`
  - `React 19 + TypeScript`
  - `shadcn/ui`
  - `Tailwind CSS 4`
  - `Zustand`
  - `TanStack Query`
- 主面板保留摘要视图，`Permissions & Safety` 作为独立子页面进入。
- 权限模型固定为两层：
  - `系统授权状态`
  - `Companion 使用开关`
- 权限页内部采用：
  - 顶部摘要条
  - 分组列表
  - 当前页详情展开区
- 每个权限项采用紧凑列表样式：
  - 名称
  - 一句用途说明
  - 状态标签
  - 右侧开关
  - 详情入口
- 高风险能力单独分组，不与系统权限混排。
- 所有高风险能力默认关闭。
- `管理员动作` 保持逐次确认，不提供“长期放行”。

## Why this fits the current architecture

当前 companion 已经具备托盘壳、状态采集、Tauri 命令桥接和状态推送能力。此前前端长期集中在一张手写单页里；现在已经迁到 `/Users/songsu/Desktop/trapezohe-companion/tray/ui-react`。随着更新、日志、设置、多语言、权限控制不断增加，统一到组件化前端之后，后续维护和扩展会更稳定。

另一方面，后端侧已经有较清晰的运行状态模型与命令能力，真正缺的是：

- 一个可维护的前端组件结构
- 一套明确的权限与安全模型
- 插件动作日志与权限状态之间的统一表达

因此，这次不只是补一个权限页，而是顺势把整个 companion 面板一起迁到 React 组件化结构上。这样后面继续加设置、更新、日志和权限控制时，不会再回到“大文件里硬堆逻辑”的状态。

## UI architecture

### 1. 整体页面结构

新的托盘面板固定组织为以下几个区域：

- `Overview`
  - 服务状态
  - MCP 服务状态
  - 更新状态
  - 权限与安全摘要入口
- `Permissions & Safety`
  - 系统权限分组
  - 高风险能力分组
  - 权限详情展开区
- `Plugin Action Logs`
  - 只显示插件调用 companion 的动作日志
- `Settings`
  - 语言
  - 开机启动
  - 重启服务
  - 退出
  - 其他全局设置

整个面板仍按“状态栏下方的窄面板”设计，不走普通客户端宽页面布局。

### 2. 主面板中的权限入口

主面板不直接展开所有权限项，只显示一条摘要入口，例如：

- 已启用多少项
- 有多少项需要处理
- 高风险能力当前关闭多少项

用户点击后进入独立的 `Permissions & Safety` 子页面。

这样做的原因：

- 主面板保持简洁
- 权限页可以容纳完整说明与引导
- 不会把首页做成一张“什么都塞进去”的混合设置页

### 3. 权限页结构

权限页固定分为三层：

#### 顶部摘要

展示权限总览：

- 已启用数量
- 需要处理数量
- 高风险能力关闭数量

#### 分组列表

按组展示：

- `系统权限`
- `高风险能力`

#### 当前页详情展开区

点击某项后，在当前页内展开详情区，不另外弹全屏窗体。

详情区固定显示：

- 这项能力是做什么的
- 当前系统状态
- 当前 Companion 开关状态
- 打开后会发生什么
- 去系统设置授权的入口
- 查看相关日志的入口

## Permission model

### 1. 双层状态模型

每个权限项始终独立表达两件事：

- `系统授权状态`
  - 已授权
  - 未授权
  - 当前平台不支持
- `Companion 使用状态`
  - 已开启
  - 已关闭

这两层不能混成一个开关，也不能让“系统授权了”自动等于“Companion 正在使用”。

### 2. 关闭行为

当用户把某项能力从开启切回关闭：

- 只关闭 Companion 对这项能力的使用
- 不撤销系统权限
- UI 明确显示为：
  - 系统已授权
  - Companion 已关闭

### 3. 打开行为

当用户把某项能力从关闭切到开启：

- 如果系统已授权：
  - 直接开启 Companion 使用
- 如果系统未授权：
  - 不显示假开启状态
  - 开关仍保持关闭
  - 展开详情区并提示：
    - 需要先去系统设置授权
    - Companion 在拿到授权前不会启用这项能力

### 4. 不支持的平台

如果某项权限在当前平台不存在或暂未支持：

- 直接显示“当前平台不支持”
- 开关禁用
- 不把它展示成故障或异常

## Permission groups

### 1. 系统权限

首版纳入：

- 屏幕录制
- 辅助功能
- Automation
- 相机
- 麦克风
- 定位
- 通知

其中以 macOS 为主完成真实检测与授权引导；其他平台如果尚未支持完整检测，先统一走“平台不支持 / 暂未支持”表达，不伪装成可用。

### 2. 高风险能力

首版纳入：

- 本地命令执行
- 浏览器控制 / UI 自动化
- 管理员动作

这组能力统一特点：

- 默认关闭
- 需要显著风险提示
- 开启动作必须有用户确认

## Permission row design

每个权限项采用紧凑列表行，适配托盘窄面板。

### 固定内容

- 名称
- 一句用途说明
- 两类状态标签
- 右侧开关
- 详情入口

### 状态标签规则

优先用短标签表达，而不是长段落堆说明：

- 系统状态类：
  - `系统已授权`
  - `系统未授权`
  - `当前平台不支持`
- Companion 状态类：
  - `Companion 已开启`
  - `Companion 已关闭`
- 风险类：
  - `高风险`
  - `默认关闭`
  - `每次都确认`

高风险项的风险解释放到详情区，不在列表区长篇展示。

## High-risk capability behavior

### 1. 启用前确认

当用户第一次开启某个高风险能力时，先弹出确认框，再真正切换开关。

确认框固定说明：

- 这项能力能做什么
- 可能带来的影响
- 开启后日志会记录什么

底部按钮固定为：

- `取消`
- `确认启用`

### 2. 本地命令执行

说明重点：

- 能执行本地命令和脚本
- 可能修改文件、读取环境、启动进程
- 默认关闭

### 3. 浏览器控制 / UI 自动化

说明重点：

- 能控制浏览器、点击元素、输入内容、读取页面信息
- 可能触发网页上的真实操作
- 默认关闭

### 4. 管理员动作

说明重点：

- 涉及更高系统权限的敏感操作
- 风险最高
- 默认关闭
- 即使总开关开启，也要逐次确认

### 5. 管理员动作逐次确认

每次真正执行管理员动作时，都必须再次弹确认框，不能只依赖总开关。

确认框至少显示：

- 这次要执行什么
- 由哪个插件动作触发
- 为什么需要管理员权限
- 影响范围是什么

按钮固定为：

- `取消`
- `继续执行`

本轮不支持：

- 永久放行
- 限时免确认
- 自定义白名单策略

## Plugin action logs

### 1. 日志范围

这里只记录：

- 插件调用 companion 执行动作的日志

不混入：

- daemon 内部运行日志
- 打包日志
- 调试日志
- 心跳、自检、轮询

### 2. 每条日志最少字段

- 时间
- 触发来源
- 调用了哪类能力
- 结果状态
- 一句简短原因

### 3. 日志状态枚举

界面层统一使用：

- `已执行`
- `等待确认`
- `被权限拦截`
- `系统未授权`
- `用户取消`
- `执行失败`

### 4. 权限相关日志映射

需要明确区分：

- Companion 开关没开
  - 结果：`被权限拦截`
  - 原因：例如 `本地命令执行未启用`
- 系统层没授权
  - 结果：`系统未授权`
  - 原因：例如 `辅助功能未授权`
- 用户取消确认
  - 结果：`用户取消`
  - 原因：例如 `管理员动作已取消`
- 实际执行时报错
  - 结果：`执行失败`
  - 原因：保留简短错误说明

### 5. 日志与权限页联动

权限详情区提供 `查看相关日志` 入口，只看与该权限项相关的最近记录。

例如在“辅助功能”详情里，可以看到：

- 哪次调用因为系统未授权被拦住
- 哪次在授权后成功执行

### 6. 主状态与权限失败解耦

如果某次插件动作因为权限未启用或未授权而未执行：

- 该情况必须写入动作日志
- 但主服务健康状态不能因此显示成“服务坏了”

因为这属于权限条件未满足，不属于 companion 自身崩溃或失效。

## Frontend runtime design

### 1. 技术栈

新前端固定使用：

- `React 19 + TypeScript`
- `shadcn/ui`
- `Tailwind CSS 4`
- `Zustand`
- `TanStack Query`

不再继续把新功能写入旧单页结构作为长期方案。

### 2. 组件拆分

建议至少拆成以下组件：

- `PanelShell`

- `PermissionSummaryCard`
- `PermissionGroupSection`
- `PermissionRow`
- `PermissionDetailPanel`
- `RiskConfirmDialog`
- `AdminActionConfirmDialog`
- `ActionLogList`
- `ActionLogDetailDialog`
- `SettingsSheet`

### 3. 状态管理分工

`TanStack Query` 负责：

- 服务状态快照
- 更新检查
- 权限状态刷新
- 后端异步命令结果

`Zustand` 负责：

- 当前打开的页面
- 当前选中的权限项
- 哪个抽屉 / 弹框处于打开状态
- 本地 UI 偏好
- 日志筛选条件

`Tauri event` 负责：

- 后端状态变化推送
- 前端收到后更新 Query 缓存

## Migration rules

### 1. 不长期并存两套 UI

不采用“旧首页 + 新权限页”的长期混搭方案。

可以存在短期迁移分支，但最终交付时：

- 主面板
- 权限页
- 日志页
- 设置页

都应统一在 React 前端中。

### 2. 现有功能不丢

UI 重构不能牺牲现有能力，包括：

- 服务状态展示
- MCP 服务展示
- 更新检查与安装入口
- 日志查看
- 设置
- 多语言

## Error handling

- 系统未授权：
  - 开关不进入假开启态
  - 提示去系统设置授权
- 高风险启用被取消：
  - 开关保持关闭
  - 写入动作日志
- 管理员动作被取消：
  - 写入 `用户取消`
  - 不改变主服务健康状态
- 当前平台不支持：
  - 明确标注
  - 不显示成错误
- 权限检测失败：
  - 在详情区给出简短错误说明
  - 保留重新刷新入口
